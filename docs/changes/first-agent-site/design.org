#+OPTIONS: ^:{} -:nil

* Context
The repository holds no code at the change's base: specs, glossary, research and this change's intent only. Everything is new. The stack is TypeScript with Vitest (=npx vitest run=); React draws the page in the browser, a small Node server holds the Claude key and the allowlist. The test tree sits beside the code as =*.test.ts= under =src/=; renderer tests run under jsdom. The package manifest and the Vitest configuration (which excludes =.worktrees/=, where task worktrees keep their own copies of the tests) exist so the pending tests run and report as pending; the first task adds the runtime dependencies.

Layout the seams assume: =src/shared/= holds what both sides use and imports no renderer or DOM (page spec, tool definitions); =src/client/= holds the page store, the agent loop and the renderer under =src/client/render/react/=; =src/server/= holds the server, the model proxy and the fetch tool.

* Decisions

** D1: The page spec and its edits are a renderer-free module (seam/page-spec-core)
Every change to the page goes through one edit function that validates against the catalog before anything changes, so the assistant, the store and any future renderer see one set of rules and a rejected edit is indistinguishable from no edit. The spec says the renderer is swappable; this is where that holds. Edits are add-or-replace by id, remove, and set data.

** D2: The tool list is defined once (seam/tool-list)
The server pins the tool list, the browser runs the page-spec tools, the server runs the fetch tool. One definition feeds both sides, so the list the model sees and the executors the browser binds cannot drift.

** D3: The visitor's page lives in one browser-only store (seam/page-store)
The store is the only holder of the current page spec and of the one copy kept before a turn; the renderer reads it, the loop's tools write it. Nothing is persisted, so a reload is a new store holding the skeleton. Undo is one step back because the store keeps one copy.

** D4: The loop does not know the page or the network (seam/agent-loop)
The loop takes the model call, the tool executors and the before-turn hook as inputs, and reports its state. That keeps every state and transition testable with a fake model, which is the point of writing it by hand. Stopping a turn cancels the loop; edits already applied stay because the store, not the loop, owns them.

** D5: The browser never holds the key and never chooses the prompt or tools (seam/model-proxy)
The server forwards the conversation to the model with its own key, system prompt and tool list and ignores any the browser sends. The server keeps nothing between requests.

** D6: One fetch path, checked at every hop (seam/allowlist-fetch)
Every URL the tool is asked for, including each redirect target, is checked against the allowlist, and the host's resolved address is checked when the connection is made. The server adds the host's secret; the result carries neither the secret nor more than the size limit.

* Open Questions

Each entry's rows and tests are drafted in the recommended form; none has a Decision until the user answers.

** Q1 (intent): Which data sources does the first test use?
Options: (a) one free keyless API such as Open-Meteo weather: nothing to configure, secret injection untested by hand; (b) one keyless and one keyed API: every data-fetch requirement is exercised from the start, the owner supplies one key. Recommendation: (b), so the secret path is played with, not only unit-tested. Depends on: data-fetch § Fetch then display; the owner's allowlist file. No seam row or pending test changes with the answer.

** Q2 (intent): Adopt json-render, or define our own page spec in its shape?
Options: (a) adopt json-render: a ready renderer, but its format and versioning belong to someone else and the swappable-renderer requirement leans on its adapters; (b) our own minimal spec in json-render's shape, edited by the three edit operations: more to write, fully visible. Recommendation: (b), matching the experiment's aim of visible mechanics (E2). Depends on: seam/page-spec-core, seam/page-renderer, seam/tool-list and their pending tests, all drafted as (b); with (a) they are re-run scoped to those rows.

** Q3 (intent): Does the hand-written loop run in the browser or on the server?
Options: (a) browser loop behind a proxy that fixes the system prompt and tool list: every state visible in the page, the page-spec tools run where the page is; (b) server loop that hands page-spec tool calls to the browser: prompt and tools are enforced only server-side, but the loop is split across two places. Recommendation: (a). Depends on: seam/agent-loop, seam/model-proxy, seam/tool-list and their pending tests, all drafted as (a); with (b) they are re-run scoped to those rows.
