#+OPTIONS: ^:{} -:nil

* Context
At the change's base (0d4b75e) and at the round's HEAD the repository holds no code: the research effort (=research/dynamic-agent-site/=), the intent, the three spec files =page-spec=, =agent-loop= and =data-fetch= under =docs/specs/=, the glossary, and the orchestrator overlay (=language: typescript=, test command =npx vitest run --reporter=junit --passWithNoTests=, pending style Vitest =it.fails=). Everything below is new.

The research settled what the design starts from: the assistant edits a page spec over a fixed component catalog and never writes markup; changes are for the visitor who made them and are gone on reload; a small stateless server owned by the site's owner holds the Claude key and the data secrets and is the only party that calls the Messages API or a data API; the loop is hand-written over the Messages API; undo is one turn back (brief § Decided). E3 found the loop to be about thirty lines, the browser-loop and server-loop placements to cost the same model round trips, and fetched payloads to be best kept out of the model's context; E2 found the declarative page specs of prior art converging on a flat id-keyed component map, a separate data model bound by path, and coarse upsert/remove tools.

The round's four open questions were answered by the user at the first plan (cycle-1793231989), each on its recommendation: D10 to D13. The rows drafted in the form those recommendations implied stand as written.

* Decisions

** D1: One TypeScript package: the page, the owner's server, the tests
The page is React 19 built by Vite, under =src/=. The owner's server is under =server/= as a fetch-style request handler made by =createApp= from its configuration; a small Node entry runs it and serves the built page, and in development Vite's dev server sits in front of it. No web framework and no agent framework (agent-loop § Hand-written, no agent framework). How charts are drawn is the Implementor's choice inside seam/catalog. Why: R4 asks for React and one build; R5 for a small server; one language lets the server import the very tool list the browser runs (seam/tool-list); a handler that takes a request and returns a response runs in-process under test.

The round wrote the scaffold the tests need: =package.json= with exact versions (React, Vitest, jsdom, Testing Library, TypeScript), =.npmrc= with =legacy-peer-deps= (npm 10.9 fails to resolve jsdom's optional =canvas= peer without it, observed this round), =vite.config.ts= whose junit reporter prints to standard output so the overlay's test command carries its report, and =tsconfig.json=.

** D2: The tests drive the whole site in one process, with the model and the internet scripted
Every test runs the page and the owner's server together: the page drawn in jsdom, its requests to its own origin answered by =createApp='s handler, and the server's two ways out, the Messages API and the data hosts, each replaced at the server's edge by a scripted fake (=test/support/site.ts=). So the scenario tests are acceptance tests: they act as the visitor does (type, send, stop, undo, press) and assert on what the page shows, what the model was sent and what the data hosts received. They hold whichever side the loop runs on (Q3). What the design must keep for this: the page reaches the server with =fetch= on its own origin only; the server's requests to the Messages API and to data hosts each go through one replaceable function given to =createApp=, with the server's own connection-checked transport as the data default; no state of a page outlives the page's modules, so a reload is fresh modules over the same browser storage. The page is found by accessible roles and names, and drawn components by their page-spec id and type; the exact roles, names and marks are the ones the harness and the tests use. No test talks to the real model: the intent rules out a scripted acceptance suite of conversations, and these tests script the model only to pin the mechanics.

** D3: Fetched data reaches the page without passing through the model (seam/fetch-result)
The fetch tool's whole response goes to the browser and is kept in the page spec's data under a name the assistant gives; the model reads only a view of it cut to a size limit, and binds components to the data by name. Why: E3 found that letting the model choose the display while the data goes straight from the API to the component is what keeps large payloads affordable, and data-fetch § Large responses are trimmed then limits only what the model reads, never what a chart draws. The cost: the page spec can hold large data, so what the model is told about the page names the data by its shape (D4).

** D4: Each visitor message carries the page as it stands (seam/page-snapshot)
Undo and stopping change the page between turns without the model's doing, and the conversation is append-only (E3 § 4: editing earlier turns invalidates replayed thinking). So the model is never told the page by rewriting history; each visitor message it receives carries a description of the current page: every component with its id, type and props, and the data by name and shape.

** D5: Undo restores the page spec only (seam/page-store)
Undo puts back the copy of the page spec taken when the last turn started, page-spec § Undo the assistant's last turn. The chat and the model's conversation keep the undone turn; the model learns of the change from the next visitor message (D4). One step only: a second undo before another turn changes nothing. Undo is offered between turns, not while one runs.

** D6: What a stopped turn leaves (seam/stop)
Stopping aborts the turn's model request or tool run and the loop goes to awaiting the visitor. Edits already applied stay, and the copy taken at the turn's start is still what undo restores (the approved default: stopping keeps edits, undo reverts them). Nothing that arrives for the stopped turn is applied. The conversation keeps the turn's finished steps and every tool call in it is answered, so the next turn's request is valid. A tool already running when the visitor stops may still complete on the server (E3: an aborted call is not recalled); its result is dropped.

** D7: The server fixes the model, the system prompt and the tool list (seam/model-relay)
The server's code holds the model id, the system prompt and the tool list (agent-loop § Visitors need nothing but a browser), and sends them with every request; whatever else the page sends is ignored. The model starts as =claude-sonnet-5-5=: E3 names turn latency as the risk to the experience and Sonnet as the starting point; it is one constant in the server.

** D8: The allowlist is the owner's data, and nothing loads from off it (seam/allowlist)
The allowlist is a file the owner edits: each entry a host and, for a keyed host, where its secret goes and which environment variable holds it; the server reads it at start and passes the resolved list to =createApp=. Adding a source is an edit to that file (R2). The page itself loads nothing from another host: an image is fetched through the server under the same allowlist, because an image address the model writes is a request to wherever it points, and fetched data can steer the model (E3 § 3, prompt injection with a fetch is an exfiltration path).

** D9: The first component catalog (seam/catalog)
The catalog holds the types of page-spec § The first component catalog: heading, text, image, card, list, row, column, table, chart (line, bar, pie), key-figure tile, form and button. Each type's props are validated where the catalog defines it, and a prop either holds its value or binds to the page spec's data by name and path. Every prop is drawn as what it says, never as markup (the assistant writes no HTML or scripts). The tests draw heading, text, image, card, table, chart and button; the other types share the same path from the catalog to the drawing.

** D10: The first allowlist ships one keyless source and one keyed source (ask-cycle-1793231989-1)
The allowlist the first build ships holds a keyless host (Open-Meteo weather) and one host that needs a secret, so data-fetch § Secrets added by the server is tried against a real service from the start. The user left the keyed service to the Implementor: one with a free key. Its secret goes in a request header (D8); a service that takes its key in the query string adds that form to the allowlist entry. The tests script their hosts either way.

** D11: Our own page spec, in json-render's shape (ask-cycle-1793231989-2)
The page spec is this project's own minimal format, not json-render's: a flat id-keyed component map with a separate data model bound by path, edited by =put_components=, =remove_component= and =set_data=, a binding written ={"$data": "/<name>/<path>"}=. Why: the experiment's aim is visible mechanics, and E2 found the small format enough. Rows: seam/page-tools, seam/catalog, seam/renderer.

** D12: The loop runs in the browser, behind a relay (ask-cycle-1793231989-3)
The hand-written loop and the conversation live in the page (=src/agent/loop.ts=); the owner's server is a relay that adds the key and fixes the model, system prompt and tool list (D7). Why: E3 found both placements cost the same round trips and both keep the key on the server; the browser keeps every state of a turn in one place. Rows: seam/turn, seam/loop-state, seam/stop, seam/model-relay, seam/tool-list.

** D13: A form or button sends a visitor message (ask-cycle-1793231989-4)
Pressing a button sends its label, and submitting a form sends its filled-in fields, as a visitor message through the loop, as if typed; it starts a turn. The page spec holds no other action. Why: one path into the loop the page already has, and nothing code-like in the page spec. page-spec gains § A form or button acts by sending a message, scenario § A button sends a visitor message. Row: seam/page-actions.
