## Why tests missed it

The echo test ("does not return the secret when the host echoes it into a redirect address") redirects to an allowlisted https address and checks only the successful outcome; the https-only test checks that the refusal happens, not what its error says, and its redirect carries no key.

## Recommended resolution

In server/fetchTool.ts fetchAllowed, pass every error it returns after the first hop through `scrub(..., secrets)` (the not-on-allowlist refusal, the not-https refusal, the more-than-five-redirects and the not-a-URL ones), case-insensitively for the hostname, since URL parsing lowercases a key with capitals; or stop naming the redirect target in those errors and name only the allowlisted host that redirected. Add a test beside the echo test in test/data-fetch.test.ts in which the keyed host redirects to `https://<key>.off-list.example/` and to `http://api.keyed.example/<key>`, and assert that neither outcome of fetchForTool, nor the image route's answer, holds the key. Related but distinct: hardening entry fetch-tool.md#4 (percent-encoded or parsed-JSON echoes in the body); this one is the key in plain text in an error.
