#+TITLE: E2: Prior art for agent-generated UI (generative UI)
#+OPTIONS: ^:{} -:nil

Evidence for [[file:../brief.org][the brief]]: goals R1, R2 and the open question "What does the assistant manipulate: raw DOM/HTML, or a structured page description rendered by fixed components?" (since closed: the page spec only).

Tags: [O] observed (read from the cited source); [I] inferred (my reading, or a secondary source I could not check against the primary one).

* Question

What prior art exists for agent-generated or agent-modified UI ("generative UI"), and how does each represent and deliver the UI? For each: what the model emits, whether the component catalogue is fixed or open, how incremental edits work, how tool data binds to UI, the safety model, renderer stacks, maturity and licence, and fit for "an assistant that keeps reshaping one live page".

** Google A2UI

- [O] Declarative JSON "A2UI Response": the agent sends UI intent; the client renders it with its own native components. The README's phrase is "safe like data, but expressive like code". Source: [[https://github.com/google/A2UI][google/A2UI]]. Revised 2026-10-28: a2ui.org now links the repo as [[https://github.com/a2ui-project/a2ui][a2ui-project/a2ui]], and the raw README is identical at both paths.
- [O] There are four server→client messages, each carrying a ="version"= field ("v0.9" or "v0.9.1"):
  - =createSurface= (=surfaceId=, =catalogId=, optional =theme=, =sendDataModel=)
  - =updateComponents= (a flat =components= array)
  - =updateDataModel= (a JSON Pointer =path= plus =value=; upsert, and omitting =value= deletes)
  - =deleteSurface=
  Source: [[https://raw.githubusercontent.com/google/A2UI/main/specification/v0_9/docs/a2ui_protocol.md][A2UI v0.9 protocol]]; re-checked against [[https://a2ui.org/specification/v0.9.1-a2ui/][v0.9.1 on a2ui.org]]. That version also standardises the =application/a2ui+json= MIME type.
- [O] It is an adjacency list. Components are flat; parents list child ids; exactly one component has id =root=. Updates are buffered until =root= arrives. The flat design is chosen because it is "easier for LLMs to generate incrementally".
- [O] Binding: ={"path": "/abs/pointer"}=, relative paths inside templates, ={"call": ...}= for registered functions, and =formatString= with =${...}=.
- [O] Client→server: an =action= event (=name=, =surfaceId=, =sourceComponentId=, =context=), plus an =error= message for validation failures. Local =functionCall= actions never leave the client.
- [O] Catalogs: the client advertises =supportedCatalogIds= and optional =inlineCatalogs=. Custom components come through a registry. Revised 2026-10-28: a catalog is "a JSON Schema file outlining the components, functions, and themes that agents can use", and "all A2UI JSON sent from the agent is validated against the chosen catalog" ([[https://a2ui.org/concepts/catalogs/][Catalogs]]).
- [O] Revised 2026-10-28, previously "the spec does not say whether re-sending an existing id replaces the component or merges into it". The spec still only says components are "added to or updated". The reference implementation settles it:
  - When an existing id arrives again, =@a2ui/web_core= 0.14.0 (=processing/message-processor.js=, =applyComponentUpdate=) sets =existing.properties = properties=, so the new props replace the old ones and are not merged.
  - If the component type or catalog changes, it deletes the component and creates it again.
  - A batch with a duplicate id is rejected.
  - There is no remove-component message. A component leaves the tree when its parent's =children= list no longer names it (orphans are governed by an =allowOrphanComponents= validation option).
- [O] Transport is not defined; A2UI can travel over A2A, AG-UI or MCP. Revised 2026-10-28: the roadmap also lists REST and WebSockets as complete ([[https://a2ui.org/roadmap/][Roadmap]]). Over MCP, a resource can hold a static template (=createSurface= + =updateComponents=), and each tool result then returns only an =updateDataModel= ([[https://a2ui.org/guides/a2ui_over_mcp/][A2UI over MCP]]).
- [O] Status: "early stage public preview". v0.9.1 is current and stable, v1.0 is a release candidate, licence Apache-2.0. Confirmed on [[https://a2ui.org/][a2ui.org]] 2026-10-28.
- [O] v1.0 (candidate) is not a drop-in successor ([[https://a2ui.org/specification/v1.0-evolution-guide/][v1.0 evolution guide]]):
  - Bindings become =@path= and =@call=.
  - =theme= is removed.
  - Components and initial data can be sent inside =createSurface=.
  - Catalogs gain =allowedParents= and =allowedChildren=.
  - Bidirectional RPC is added (=callRendererFunction=, =callAgentFunction=).
  - "client" and "server" are renamed renderer and agent.
- [O] Renderers. Revised 2026-10-28, previously "Lit, Angular and React on npm. Flutter (via GenUI SDK) and SwiftUI are not yet published". The [[https://a2ui.org/reference/renderers/][renderers page]] lists:
  - React, Lit, Angular and Flutter (GenUI SDK) as stable for v0.8 and v0.9.1, with v1.0 support planned.
  - Jetpack Compose as alpha on v0.9.1, and SwiftUI as planned.
  - All web renderers share =@a2ui/web_core=.
  - The React renderer exposes =<A2UISurface>=. It was launched in Q2 2026; the first npm release was 2026-03-17 and the latest is 0.14.0, from 2026-10-17.
  - The same page lists json-render as an "ecosystem renderer" for A2UI catalogs.

** Vercel json-render

- [O] The model emits a flat JSON spec: =root= plus an =elements= map, where each element has =type=, =props= and =children=. Revised 2026-10-28: the spec can also carry an initial =state= object, and lists use a =repeat= field (=statePath=, =key=) with =$item= / =$index= ([[https://json-render.dev/docs/data-binding][Data binding]]).
- [O] The catalog is defined with =defineCatalog= and Zod prop schemas; =catalog.prompt()= generates the system prompt from it.
- [O] State expressions: =$state=, =$bindState= for forms, =$cond=/=$then=/=$else=, =$template=, =$computed=; elements can also carry =visible= conditions. Actions use =emit=, a built-in =setState=, and a =watch= field.
- [O] Streaming: =createSpecStreamCompiler= yields partial specs and patches. Revised 2026-10-28: SpecStream is JSONL in which "each line is a JSON patch operation" (RFC 6902: add, remove, replace, move, copy, test) against JSON Pointer paths such as =/elements/card-1/props= ([[https://json-render.dev/docs/streaming][Streaming]]). The model writes this into its text output, and the server transform =pipeJsonRender()= separates text from patches.
- [O] Renderers: React, Vue, Svelte, Solid, React Native, Remotion, React PDF, React Email, Ink, Satori, R3F, Next.js and TanStack Start. Licence Apache-2.0, about 18.8k stars (stars not re-checked). Source: [[https://github.com/vercel-labs/json-render][vercel-labs/json-render]].
- [O] Revised 2026-10-28, was [I] from InfoQ: first released January 2026. =@json-render/core= and =@json-render/react= 0.0.1 and 0.1.0 were published to npm on 2026-01-14. The latest is 0.21.3 (2026-10-24), after 33 React releases.
- [O] Revised 2026-10-28, was [I] from a third-party page: =@json-render/core= 0.14.0 added "universal edit modes … for multi-turn spec refinement: =patch= (RFC 6902), =merge= (RFC 7396), and =diff= (unified diff)", with helpers =deepMergeSpec()=, =diffToPatches()= and =buildEditUserPrompt()=. It also added a YAML wire format, =@json-render/yaml= ([[https://raw.githubusercontent.com/vercel-labs/json-render/main/packages/core/CHANGELOG.md][core CHANGELOG]]).
- [O] Added 2026-10-28: an =@json-render/mcp= package integrates with MCP Apps. The [[https://json-render.dev/docs/a2ui][A2UI page]] says the core is "schema-agnostic": you "define a catalog that matches A2UI's format and build a renderer that understands it". Its example uses the v0.8 shape, and nothing in it reads A2UI messages for you.

** Thesys C1 and OpenUI

- [O] Revised 2026-10-28, was [I] from snippets. C1 is an OpenAI-compatible endpoint (base URL =https://api.thesys.dev/v1/embed=) that returns "a UI specification object (C1 DSL)". The response uses "an XML-like structure to package multiple types of content into a single string" ([[https://docs.thesys.dev/legacy/guides/how-c1-works.md][How C1 works]]). The client renders it with =<C1Component>= or =<C1Chat>= from =@thesysai/genui-sdk=, whose peer dependency is =@crayonai/react-ui= ([[https://docs.thesys.dev/legacy/guides/rendering-ui.md][Rendering]]). Responses can be streamed.
- [O] *Correction 2026-10-28:* the C1 docs are now an archive under =/legacy=, "kept online for teams already running C1 in production. New projects should start with the OpenUI docs." OpenUI is "the actively developed successor to C1" ([[https://docs.thesys.dev/legacy/index.md][C1 archive]]). The C1 row's fit is lowered from med to low.
- [O] Revised 2026-10-28, partly confirmed. [[https://www.openui.com/docs][OpenUI]] is built on OpenUI Lang, "a streaming-first language with first-party runtimes for React, Vue, Svelte, and Angular". The earlier text omitted Angular. The renderer draws "each component as its line arrives", and components are defined with Zod. The licence is MIT ([[https://www.openui.com/docs/openui-lang/comparison][comparison]]).
- [I] Vendor claims, not checked independently: "up to 67% fewer tokens than JSON", and roughly 3x fewer tokens than json-render or A2UI in Thesys's own benchmark. Thesys also ships an =@openuidev/a2ui= package for A2UI v1.0. OUI-1 (Sep 2026), a model fine-tuned to emit OpenUI Lang, is still only from secondary sources ([[https://mer.vin/2026/05/openui-lang-mit-generative-ui-that-cuts-llm-output-tokens-versus-json/][mer.vin]], [[https://rits.shanghai.nyu.edu/ai/oui-1-diffusion-model-generative-ui/][NYU RITS]]). Why added: a third point in the format space, a DSL rather than JSON or HTML.

** AG-UI protocol and CopilotKit

- [O] AG-UI is an event-based protocol (about 16 standard event types) between an agent backend and a frontend: state sync, frontend tools, human-in-the-loop. It is MIT-licensed with about 16.9k stars and many framework integrations (LangChain, Mastra, Google ADK, Claude Agent SDK, and others). MCP Apps support is listed. Source: [[https://github.com/ag-ui-protocol/ag-ui][ag-ui-protocol/ag-ui]].
- [I] The run lifecycle is =RUN_STARTED= … =RUN_FINISHED= or =RUN_ERROR=. State moves as =STATE_SNAPSHOT= or as =STATE_DELTA= carrying RFC 6902 JSON Patch. Transport is SSE or WebSocket ([[https://agentwiki.org/ag_ui_protocol][agentwiki]]).
- [I] CopilotKit names three generative-UI patterns ([[https://copilotkit.ai/blog/the-developer-s-guide-to-generative-ui-in-2026][CopilotKit guide 2026]]):
  - static: a tool call renders a prebuilt component (=useFrontendTool= / =useRenderTool=)
  - declarative: an A2UI or Open-JSON-UI spec
  - open-ended: MCP Apps HTML
  Some docs add a fourth, "Open Generative UI" (raw HTML/SVG).
- [I] AG-UI is a transport and state channel, not a UI format. Its =STATE_DELTA= JSON Patch is a ready mechanism for "page description as shared state".

** Vercel AI SDK generative UI and v0

- [O] AI SDK UI (v5+): a server tool call appears as a message part typed =tool-${toolName}=. The client switches on =part.state= (=input-available=, =output-available=, =output-error=) and renders an app-owned React component from =part.output=. The model chooses which tool to call and what arguments to pass; it never writes the UI itself. Revised 2026-10-28: confirmed against the primary page. The docs say "Generative UI is the process of connecting the results of a tool call to a React component", and "In AI SDK 5.0, tool parts use typed naming: =tool-${toolName}=" ([[https://ai-sdk.dev/docs/ai-sdk-ui/generative-user-interfaces][AI SDK docs]]).
- [O] AI SDK RSC =streamUI= streams server React components from tool output. Revised 2026-10-28: confirmed against the primary pages.
  - The overview says "AI SDK RSC is currently experimental. We recommend using AI SDK UI for production" ([[https://ai-sdk.dev/docs/ai-sdk-rsc/overview][RSC overview]]).
  - The migration guide lists three problems: aborting a stream is "not possible" with server actions; components "remount on =.done()=, causing them to flicker"; and =streamUI= "does not support multi-step tool calls" ([[https://ai-sdk.dev/docs/ai-sdk-rsc/migrating-to-ui][migrating to UI]]).
- [I] v0 (renamed v0.app in Jan 2026) generates React + Tailwind + shadcn source code. Generated components install into a codebase via =npx=. It is a code generator, not a runtime UI channel ([[https://resources.rework.com/tools/ai-coding/lovable-vs-bolt-new-vs-v0][rework comparison]]).
- [I] The UI pattern is chat-scoped: each component sits inside a chat message. It is not one persistent page.

** MCP Apps (SEP-1865) and MCP-UI

- [O] UI is a predeclared =ui://= resource with MIME type =text/html;profile=mcp-app=. A tool links to it through =_meta.ui.resourceUri=.
- [O] The spec rejects embedding UI in tool results; the resource "MUST exist on the server", so hosts can review it before a tool runs. Per-call data arrives as =ui/notifications/tool-result=. Source: [[https://raw.githubusercontent.com/modelcontextprotocol/ext-apps/main/specification/2026-01-26/apps.mdx][MCP Apps spec 2026-01-26]].
- [O] Sandbox: the View runs in a sandboxed iframe. Web hosts must use a sandbox proxy on another origin. The default CSP is =default-src 'none'= and =connect-src 'none'=, and nested frames are blocked.
- [O] The View can call =tools/call=, =resources/read=, =ui/message= and =ui/update-model-context=. Messages are JSON-RPC over postMessage.
- [O] Status: stable as of 2026-01-26; host support in Claude, ChatGPT, VS Code, Goose and others; Apache-2.0 ([[https://github.com/modelcontextprotocol/ext-apps][ext-apps]]).
- [O] MCP-UI pioneered the idea and now implements MCP Apps. It offers =AppRenderer= and the legacy =UIResourceRenderer=, which also comes as a Web Component, with resource kinds =rawHtml=, =externalUrl= and =remoteDom=. 5.2k stars, Apache-2.0 ([[https://github.com/MCP-UI-Org/mcp-ui][mcp-ui]]). Revised 2026-10-28: confirmed on [[https://mcpui.dev][mcpui.dev]]. It reads "MCP-UI is now standardized into MCP Apps", the packages "implement the spec, and serve as a community playground", and "all remote code executes in sandboxed iframes". The site documents =AppRenderer= from =@mcp-ui/client= and a "Legacy MCP-UI Adapter". Its licence is Apache 2.0.
- [I] The model does not author the UI: a developer writes it, and the model only triggers it. That fits "prebuilt widgets in someone else's chat host", not reshaping a site.

** OpenAI Apps SDK

- [O] Revised 2026-10-28, was [I] from Skybridge and sunpeak. Source: [[https://developers.openai.com/apps-sdk/build/chatgpt-ui][Add UI to your MCP server]].
  - "ChatGPT implements the open MCP Apps" standard. Components "run inside an iframe in ChatGPT, communicate with the host through the MCP Apps bridge", and the UI resource uses =mimeType: "text/html;profile=mcp-app"=.
  - =window.openai= is a set of "compatibility aliases" that "remain available for existing integrations. New UI should use the shared fields". The docs pair each alias with its MCP Apps equivalent:
    - =_meta["openai/outputTemplate"]= → =_meta.ui.resourceUri=
    - =window.openai.toolOutput= → =ui/notifications/tool-result= (=structuredContent=)
    - =callTool= → =tools/call=
    - =sendFollowUpMessage= → =ui/message=
- [O] *Correction 2026-10-28:* =setWidgetState= has no MCP Apps equivalent. It is a ChatGPT-only extension for widget-state persistence, listed alongside =requestCheckout=, file upload and =requestModal=. The portable route for telling the model about UI state is =ui/update-model-context=.
- [I] The claim that the earlier MIME type =text/html+skybridge= was replaced still rests on the secondary sources ([[https://docs.skybridge.tech/resources/apps-sdk-and-mcp-apps][Skybridge]], [[https://sunpeak.ai/blogs/migrate-openai-apps-sdk-to-mcp-apps/][sunpeak]]). The current OpenAI page no longer mentions =skybridge=.

** Claude Artifacts and Imagine with Claude

- [I] Artifacts: the model writes a whole HTML, React or SVG file. It runs in a sandboxed iframe on =claudeusercontent.com= under a CSP that limits external fetches and storage ([[https://simonwillison.net/tags/content-security-policy/][Willison]], [[https://claude.com/docs/government/security/security-and-data-handling.md][Claude Gov docs]]). Edits are rewrites or targeted string edits of the file. I found no official source for the edit mechanism; this is from general knowledge.
- [I] Added: Imagine with Claude (Sep 2025, a 5-day research preview) generated the interface live, per interaction, with no fixed codebase. Nothing persisted across refresh, and the UI changed on each click ([[https://datacamp.com/tutorial/imagine-with-claude][DataCamp]]). Why added: the closest prior art to "the assistant keeps reshaping one live page". It shows the raw-generation end of the design space and its instability.

** Google Gemini dynamic view (added)

- [I] Gemini "designs and codes a fully customized interactive response for each prompt", shipped as the dynamic view and visual layout experiments, and in Search AI Mode ([[https://research.google/blog/generative-ui-a-rich-custom-visual-interactive-user-experience-for-any-prompt/][Google Research]]). Why added: Google ships both this open-code approach and A2UI, a declarative one.

** websim.ai

- [I] The model (Claude by default) generates a complete HTML/CSS/JS page for any typed URL or prompt. Navigation generates new pages, and editing means regenerating ([[https://www.tomsguide.com/how-to-use-websim][Tom's Guide]], [[https://rentry.org/websim][rentry]]).

** tldraw make real

- [I] Captures a PNG of a sketch, and a vision model returns one Tailwind HTML file. That file renders in an iframe shape on the canvas. To iterate, the user annotates the preview and regenerates ([[https://tldraw.dev/blog/make-real-the-story-so-far][tldraw blog]], [[https://www.simonwillison.net/2023/Nov/16/tldrawdraw-a-ui][Willison]]).

** Microsoft Adaptive Cards

- [I] A JSON card schema (v1.6; Teams caps at 1.5) with =${expr}= templating that separates the template from its data. Microsoft suggests LLMs to draft card JSON. In Copilot Studio, agent instructions cannot render a card dynamically ([[https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/adaptive-cards-overview][MS Learn]], [[https://microsoft.github.io/cat-agent-skills/skills/copilot-studio-adaptive-card-builder][MS agent skills]]).
- [I] It is the pre-LLM ancestor of A2UI and json-render: a fixed schema, data binding, and host-native renderers.

** LLM site builders (contrast)

- [I] v0, bolt.new and Lovable generate full app source code (React, sometimes with a Supabase backend). The edit loop is: change code, rebuild, preview. That is a developer workflow, not a runtime page the end user reshapes ([[https://addyo.substack.com/p/ai-driven-prototyping-v0-bolt-and][Osmani]]).

** A2UI vs json-render as our page spec

Added 2026-10-28, after the brief decided two things: the assistant edits a JSON page spec over a fixed component catalogue only, and changes are per-visitor and ephemeral. The facts come from the sections above. Rows tagged [I] are my evaluation.

| Aspect | A2UI (v0.9.1) | json-render (0.21) | Tag |
|--------+---------------+--------------------+-----|
| Unit of change | A stream of four envelope messages. The page is the renderer's accumulated state, not a document. | One spec document (=root=, =elements=, =state=). Changes are RFC 6902 ops on it. | O |
| Edit granularity | Whole component by id (props replaced, not merged). Data by JSON Pointer path. No remove-component message: remove by rewriting the parent's =children=. | Any JSON Pointer path, down to one prop, including =remove= and =move=. Edit modes: patch, merge, diff. | O |
| Data binding | ={"path": ...}= (=@path= in v1.0), relative paths in templates, =formatString=, catalogue functions. Data model kept separate per surface. | =$state=, =$bindState=, =$item= / =$index= with =repeat=, =$cond=, =$computed=. State sits inside the spec or in a =StateProvider=. | O |
| Catalogue definition | A JSON Schema file with a =catalogId=, negotiated through =supportedCatalogIds= / =inlineCatalogs=, plus per-framework component code. v1.0 adds parent/child constraints. | Zod schemas in TypeScript (=defineCatalog=) mapped to components (=defineRegistry=). =catalog.prompt()= writes the system prompt; 36 prebuilt shadcn components. | O |
| Streaming of partial specs | Message by message (JSONL, SSE, WS). Rendering waits until =root= arrives, then shows placeholders for missing refs. No partial messages. | Line-level patches; =createSpecStreamCompiler= yields a partial spec after each line. | O |
| React renderer | Official =@a2ui/react= on =@a2ui/web_core=. Stable for v0.9.1, first published Mar 2026, now 0.14.0. No v1.0 support yet. | =@json-render/react=, the first and main renderer. Published since Jan 2026, now 0.21.3 across 33 releases. Many sibling renderers. | O |
| Maturity | "Early stage public preview". A v1.0 RC that renames binding keys is pending. | Pre-1.0 and fast-moving (21 minor versions in 10 months). | O |
| Licence | Apache-2.0 | Apache-2.0 | O |
| Native generation mode | The LLM writes "text and a JSON list of A2UI messages" from a schema-bearing prompt (=DirectJsonFormat=), and the agent parses and validates it. | The LLM writes SpecStream JSONL patches in its text, and the server splits them out (=pipeJsonRender=). | O |
| Fit to LLM tool calls | Good. Each message type maps to one tool, and its body is the tool's input schema. | Weak as-is. A generic =apply_patch(ops)= tool asks the model for RFC 6902 pointers into arrays (=children/2=), a known failure mode. It needs wrapping in coarser tools. | I |

- [I] *Could A2UI's messages be our tools verbatim?* Almost:
  - =update_components(components[])= and =update_data_model(path, value)= map one-to-one. Each component's schema is a =oneOf= over the catalogue, which tool-input JSON Schema can express.
  - =createSurface= / =deleteSurface=, =surfaceId=, =version= and catalogue negotiation serve agents sending UI across trust boundaries to renderers they do not control. With one page, one assistant and one fixed catalogue, they become constants the host fills in.
  - Two gaps for an assistant that keeps reshaping a page. Removing a component needs a separate operation, since A2UI has only "rewrite the parent's children". And whole-component replacement means a one-prop change re-sends the component; that is acceptable because components are small.
  - The v0.9→v1.0 rename (=path= → =@path=) means copying the wire format verbatim ties us to a moving version.
- [I] *Per-visitor, ephemeral state suits both.* Neither needs a server-side store. The page spec lives in browser memory and is gone on reload, as decided. json-render's single document is easier to show to the model ("here is the current page spec") and to snapshot or undo than A2UI's accumulated message state. Undo is not a goal, but it is cheap.
- [I] *Recommendation: define our own minimal page spec in json-render's document shape, edited through A2UI-style coarse tools.*
  - Spec: ={root, elements: {id: {type, props, children}}, data}=, with bindings as ={"$data": "/pointer"}=.
  - Tools: =upsert_components(components[])=, which replaces by id as A2UI does; =remove_component(id)=; =set_data(path, value)=; and a read tool that returns the current spec.
  - Catalogue: Zod schemas that generate both the tool input schemas and runtime validation.
  - Renderer: a small React registry. Because the shape matches json-render's, =@json-render/react= stays a drop-in if hand-written rendering grows.
  - Why not adopt either wholesale: A2UI's protocol layers (surfaces, version, catalogue negotiation, A2A) solve problems we do not have and are still changing. json-render's native output is in-text patch streams, not tool calls, and its expression language (=$cond=, =$computed=, =watch=) is more than the first catalogue needs.
  - What we lose: streaming partial UI inside a single tool call. Upserting component by component through tool calls gives coarse progressive rendering anyway.

* Patterns

- [O] *Three representations, one taxonomy.* CopilotKit names it directly: static (tool call → prebuilt component), declarative (JSON spec over a catalogue) and open-ended (HTML/code in an iframe).
  - Static: AI SDK UI, CopilotKit static, MCP Apps and the OpenAI Apps SDK (developer-written widgets).
  - Declarative: A2UI, json-render, OpenUI, C1, Adaptive Cards.
  - Open-ended: Artifacts, Imagine with Claude, Gemini dynamic view, websim, make real.
- [O] *The declarative systems converged on the same shape.* A flat map of components keyed by id, a separate data model bound by path, and a catalogue the client owns and advertises to the model. Seen in A2UI and json-render; [I] OpenUI Lang (one named binding per line) is the same idea in a terser syntax.
- [O] *Incremental edits are patches or upserts keyed by id, not regeneration.* A2UI uses =updateComponents= (whole-component replace by id) and =updateDataModel=. json-render uses SpecStream RFC 6902 patches plus patch, merge and diff edit modes (revised 2026-10-28: confirmed in the changelog, so this is no longer [I]). AG-UI uses =STATE_DELTA= JSON Patch. The open-ended systems regenerate whole files (websim, make real, Imagine).
- [O] *Data is kept apart from structure.* Tool results go into a data model or =structuredContent=, and the UI binds to them: A2UI paths, json-render =$state=, MCP Apps tool-result notifications, AI SDK =part.output=, Adaptive Cards templates.
- [O] *Safety follows representation.* Declarative systems are "data, not code", validated against a catalogue or schema (A2UI, json-render). Open-ended systems rely on a sandboxed iframe plus CSP (MCP Apps, Artifacts, make real).
- [I] *Layering.* A UI format (A2UI, json-render, HTML) is carried over a transport (AG-UI events, MCP, A2A). These choices are independent.
- [I] *Almost all prior art is chat-message-scoped.* Each generated UI attaches to one turn. Only websim, Imagine with Claude and the site builders treat a whole page or app as the thing being changed, and those regenerate code.

* Bearing on the design (opinion)

My evaluation, not evidence.

- *Open question "what does the assistant manipulate"* (now decided: the page spec). The prior art points to a structured page description: a flat id-keyed component map plus a data model, rendered by a fixed catalogue. It does not point to raw DOM. That is the shape A2UI and json-render converged on independently. It gives R1 cheap incremental edits (upsert by id, JSON Patch) and a simple safety story, and it is one JSON document that the browser holds for the visit.
- *R2 (fetch data, choose a display).* Keep tool results in a data model and have the model emit only bindings plus a choice of catalogue component (chart, table, card). Every declarative system does this, and it keeps API payloads out of the model's UI output.
- *Simplest thing that works (R4).* Do not adopt a whole protocol stack at first. See [[*A2UI vs json-render as our page spec][A2UI vs json-render as our page spec]]: our own minimal spec in json-render's shape, edited through A2UI-style tools, rendered by a small React registry, with =@json-render/react= in reserve. AG-UI, MCP Apps and A2A solve interoperation between hosts and agents, which we do not need for one site and one assistant.
- *Escape hatch.* Ruled out for now by the brief (no custom-HTML component). If it is ever reopened, an "HTML block" component in a sandboxed iframe (the Artifacts / MCP Apps model) would contain the risk without making raw HTML the main representation.
- *HTMX (E1).* The declarative spec is renderer-agnostic, so the server could render it to HTML fragments for HTMX just as React renders it client-side. The representation choice comes before the stack choice.
