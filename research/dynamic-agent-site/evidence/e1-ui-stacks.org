#+TITLE: E1: How front-end stacks let an agent change a live page
#+OPTIONS: ^:{} -:nil

* Question

How do candidate front-end stacks let an LLM agent change a live page's structure and content at runtime, and what does each cost? Serves brief goals R1 (skeleton reshaped from chat) and R4 (simplest stack), and the open question "raw DOM/HTML, or a structured page description".

** React with a JSON page tree and a component registry

- [I] The agent's tool emits a JSON description (type, props, children) and a fixed registry maps =type= to a React component; unknown types are ignored. The model never writes markup or code.
- [O] Vercel's json-render is a ready-made version: =defineCatalog(schema, { components, actions })= with a zod =props= schema per component; =catalog.prompt()= produces the system prompt; the spec is a flat map, =root= plus =elements= keyed by id, each with =type=, =props=, =children= (array of ids). [[https://github.com/vercel-labs/json-render][json-render README]]
- [O] json-render streams through =createSpecStreamCompiler()= with =push(chunk)= returning =newPatches=; bindings include =$state=, =$bindState= (two-way for inputs), =$cond=, =$computed=; components fire catalog actions via =emit()= and a built-in =setState= action. [[https://github.com/vercel-labs/json-render][json-render README]]
- [O] Third-party guides describe its wire format as JSON Patch (RFC 6902) over JSONL; not confirmed in the README. [[https://orchestkit.vercel.app/docs/reference/skills/json-render-catalog][OrchestKit guide]], [[https://infoq.com/news/2026/03/vercel-json-render][InfoQ, 2026-03]]
- [O] Vercel's earlier React route, AI SDK RSC (=streamUI=, server components streamed from tool calls), is "currently experimental" and "not recommend[ed] ... for stable production environments". The migration guide lists its limits: components remount on =.done()= and flicker; =createStreamableUI= can cause quadratic data transfer; streams cannot be aborted from server actions. It recommends AI SDK UI: =streamText= on the server, with =useChat= on the client rendering tool results through client components. /Corrected 2026-10-28: the earlier text said development had "paused"; neither page says that./ [[https://ai-sdk.dev/docs/ai-sdk-rsc/migrating-to-ui][Migrating from RSC to UI]], [[https://ai-sdk.dev/docs/ai-sdk-rsc/overview][AI SDK RSC overview]]
- [I] Persistence is trivial: the page is a JSON document, so storing it is a database row. Moot for now: the brief decided (2026-10-28) that the page spec lives only for one visit.
- [I] Edits are cheap and targeted: "change the chart to a bar chart" becomes a props patch on one id, with no regeneration.
- [I] Cost: someone must build and maintain the registry. The page can only contain what the registry allows, and a new kind of display needs a developer.

** React with model-generated JSX compiled at runtime

- [O] react-live and react-runner transpile a code string with Sucrase and render it in-page; the only limit on what the code can reach is a =scope= object of allowed globals. No iframe isolation is documented. [[https://npmjs.com/package/react-runner][react-runner]], [[https://commerce.nearform.com/open-source/react-live/docs/installation][react-live docs]]
- [I] Running the code in the page gives it full access to the page (cookies, the chat, API tokens in memory). It is safe only inside a sandboxed iframe, which turns this into the iframe pattern below.
- [I] Most expressive option (any chart, any form); hardest to edit incrementally, since an edit means the model rewrites the component and may break code that worked.

** HTMX

- [O] =hx-swap-oob= lets one response update elements other than the target: =true= or =outerHTML= replaces the element with the same id; =beforeend:#list= etc. target a selector. Table rows and SVG children need a =<template>= wrapper; =htmx.config.allowNestedOobSwaps= controls nested oob. [[https://github.com/bigskysoftware/htmx/blob/master/www/content/attributes/hx-swap-oob.md][hx-swap-oob doc source]]
- [O] htmx 4.0.0 was released on 2026-08-28. It stays on npm's =next= tag "until some point in early 2027", and 2.x remains =latest= and "supported indefinitely". All requests now use =fetch()=. New in core: the =<hx-partial>= tag (one response, many targets, each with its own =hx-target= / =hx-swap=), and =innerMorph= / =outerMorph= swap styles using the idiomorph algorithm, which are opt-in per swap. OOB and =<hx-partial>= swaps now run after the main swap. /Corrected 2026-10-28: the earlier text said core "moves to =fetch()= with streamed responses". Core requests are plain =text/html=, and streaming HTML comes from extensions (=hx-sse=, =hx-ws=, =hx-multipart=)./ [[https://four.htmx.org/announcements/2026-08-28-htmx-4.0.0-is-released][4.0.0 announcement]], [[https://four.htmx.org/htmx-4][Changes in htmx 4.0]]
- [O] SSE in htmx 4 is an extension, not core. =hx-sse= is a rewritten "core extension": it ships inside the htmx package (=dist/ext/=; the measured npm tarball has it at 2.5 KiB gzipped) and is loaded with its own =<script>= tag, with no =hx-ext= attribute needed. /Resolved 2026-10-28: this was listed as a source conflict. The "core" in "core extension" is where the conflict came from./ [[https://four.htmx.org/htmx-4][Changes page, "Core extensions" and "Extension loading"]]
- [I] Fit: the agent loop runs on the server, which keeps page state as server-side HTML or templates. Each tool call renders a fragment that is pushed to the browser over SSE as an oob swap. Page state and persistence come free on the server; the browser holds almost nothing.
- [I] Raw model HTML passed straight through is an XSS hole. The safe variant has the model call server templates (a server-side component registry), which is the JSON-spec pattern with HTML on the wire.
- [I] Interactive charts need a JS library initialised on swapped-in content (an =htmx:afterSwap= handler or a custom element). Forms are native and strong.

** Datastar

- [O] One script tag (11.89 KiB, README badge v1.0.4; the site says "a single 11.90 KiB file") with =data-*= attributes (=data-bind=, =data-text=, =data-on:click= with =@post()=); backend SDKs live in the repo. [[https://github.com/starfederation/datastar][datastar README]], [[https://data-star.dev/][data-star.dev]]
- [O] SSE events are =datastar-patch-elements= and =datastar-patch-signals=. By default patch-elements morphs top-level elements matched by id. Its modes are =outer= (the default, "and recommended"), =inner=, =replace=, =prepend=, =append=, =before=, =after= and =remove=. Optional data lines are =selector=, =namespace svg= / =namespace mathml= and =useViewTransition=. Per the SDK ADR, only =outer= and =inner= morph and so preserve state. =data-ignore-morph= makes an element and its children skip morphing. Confirmed on the primary pages; the =namespace= lines and =data-ignore-morph= are new this revision. [[https://data-star.dev/reference/sse_events][SSE events]], [[https://data-star.dev/reference/attributes][attributes]], [[https://cdn.jsdelivr.net/gh/starfederation/datastar@1.0.2/sdk/ADR.md][SDK ADR]]
- [O] Security: Datastar expressions "are strings that Datastar evaluates as JavaScript", so user input must be escaped (or the element marked =data-ignore=). By default the CSP must allow =unsafe-eval=. /Corrected 2026-10-28: the earlier text said "HTML is written verbatim, so the sender must sanitise". Neither primary page says that. The documented risk is that =data-*= attributes in patched HTML are code./ [[https://data-star.dev/reference/security][Security reference]]
- [I] Closest of all subjects to "server-side agent streams page edits": SSE is the protocol itself rather than an add-on, and morphing keeps focus and input values while sections change.
- [I] Smaller community than HTMX (about 5.2k GitHub stars).

** Vanilla DOM / Web Components

- [I] The simplest possible design: tools like =set_section(id, html)=, =remove_section(id)= and =insert_after(id, html)= run in the browser against the skeleton's DOM. It needs no framework, but the DOM becomes the only copy of page state; to persist it you must serialise =innerHTML= or keep a parallel model.
- [O] The safe HTML insert =Element.setHTML()= (Sanitizer API) shipped in Firefox 148 (2026-02-24). Chrome status is conflicting and Safari has none, so it is not Baseline. The advice is to feature-detect and fall back to DOMPurify; =setHTMLUnsafe()= is everywhere but does not sanitise. [[https://web-platform-dx.github.io/web-features-explorer/features/sanitizer/][web-features: Sanitizer]]
- [I] Web Components are the middle ground. The model emits =<agent-chart data-src="...">=; the browser upgrades known tags on insert, so interactivity comes from a fixed set of custom elements. A sanitiser allowlist of those tags gives a registry without a framework.

** Alpine.js

- [O] After start-up Alpine watches the DOM with a MutationObserver (=observe(document, { subtree: true, childList: true, attributes: true })=) and calls =initTree= on added elements, so agent-inserted HTML with =x-data= comes alive without extra calls. Confirmed in source; alpinejs.dev does not document it. [[https://github.com/alpinejs/alpine/blob/main/packages/alpinejs/src/mutation.js][alpine src/mutation.js]], [[https://github.com/alpinejs/alpine/blob/main/packages/alpinejs/src/lifecycle.js][src/lifecycle.js]], [[https://www.bennadel.com/blog/4605-exploring-dom-mutation-observation-in-alpine-js-3-13-5.htm][Ben Nadel, Alpine 3.13.5]]
- [O] The CSP build (=@alpinejs/csp=) avoids =unsafe-eval= and "supports most of Alpine's inline expression syntax": simple assignments (=count = 0=, =count++=) and method calls with arguments (=items.push('c')=) work. It rejects property assignments (=user.name = 'John'=), arrow functions, template literals, spread, globals (=console=, =window=, =Math=) and =x-html=. Complex logic belongs in =Alpine.data()= components. /Corrected 2026-10-28: the earlier text, from Hyva's docs, said it forbids inline mutations and method arguments. That is out of date for the current build./ [[https://alpinejs.dev/advanced/csp][Alpine CSP docs]]
- [I] Alpine directives are JavaScript expressions, so model-written Alpine markup is model-written code. Use the CSP build, with only registered =Alpine.data= components the model may reference, or strip =x-= / =@= attributes.
- [I] Usually a companion to HTMX or vanilla DOM rather than a page-state model of its own.

** Lit

- [O] "Only strings originating in template literals are parsed as HTML ... a natural safeguard against XSS". =unsafeHTML= and =unsafeStatic= take only developer-controlled strings, which "could lead to cross-site scripting (XSS)" if untrusted. Confirmed on lit.dev. [[https://lit.dev/docs/templates/directives/][Lit built-in directives]], [[https://lit.dev/docs/templates/expressions/][Lit expressions]]
- [O] A2UI ships a Lit renderer (npm), so Lit is a supported target for a standard JSON spec. [[https://github.com/google/A2UI][A2UI README]]
- [I] Good substrate for the Web Components registry above: each registry entry is a Lit element and the spec renders to tags.
- [O] No build step is required. Lit is "around 5 KB (minified and compressed)", updates "only the dynamic parts" with no virtual DOM, and needs "no compilation". It is published as CDN bundles (=lit-core.min.js=), and the only transform modern browsers need is resolving bare module specifiers (or an import map). /Upgraded 2026-10-28 from [I]./ [[https://lit.dev/][lit.dev]], [[https://lit.dev/docs/getting-started/][Getting started]], [[https://lit.dev/docs/tools/requirements/][Browser requirements]]

** Svelte 5

- [O] Components can be compiled from source text at runtime (=svelte-runtime-components=), though its example compiles on the server and dynamic-imports the output; =mount()= is the Svelte 5 entry point. [[https://sveltethemes.dev/MrGentle/svelte-runtime-components][svelte-runtime-components]]
- [O] json-render has a Svelte renderer and shadcn-svelte components. [[https://github.com/vercel-labs/json-render][json-render README]]
- [I] Same two choices as React (spec or code) with the same trade-off. Its compiler gives no special edge for agent-driven pages; the runtime-code route also needs the compiler at runtime and a sandbox.

** Preact + signals

- [O] A signal passed through the tree updates only the components that read its value, without re-rendering the components it passed through. [[https://preactjs.com/blog/introducing-signals/][Introducing Signals]]
- [I] Fits a streamed, patched spec well: one signal per node id, so a patch to one node touches one component. About 4 KB plus signals; can run buildless with =htm=.
- [I] No ready-made spec renderer found this pass (json-render lists React, Vue, Svelte and Solid, not Preact; =preact/compat= may cover React's).

** Added: declarative spec protocols (json-render, A2UI)

Added because they standardise the "structured page description" side of the brief's open question across frameworks, so the choice of spec is separate from the choice of framework.

- [O] A2UI: the agent sends JSON components as a flat list referencing each other by id, plus a data model. The client renders only from its catalog of pre-approved components ("safe like data, but expressive like code"). It ships renderers for Lit, Angular and React (npm), with Flutter and SwiftUI in progress; v0.9.1 is current and v1.0 is a release candidate. It describes itself as early-stage. [[https://github.com/google/A2UI][google/A2UI]]
- [O] A2UI is transport-agnostic (SSE, WebSockets, A2A, AG-UI). From a search summary. [[https://landscape.jimmysong.io/projects/a2ui/][landscape entry]]
- [O] json-render covers React, Vue, Svelte, Solid, React Native and more under Apache-2.0, launched 2026-01. [[https://infoq.com/news/2026/03/vercel-json-render][InfoQ]]

** Added: sandboxed iframe (MCP Apps / artifact pattern)

Added because it is the only safe home for model-written HTML+JS, which is what the "generated JSX" and "raw HTML with scripts" routes produce.

- [O] MCP Apps (SEP-1865, Final; stable around 2026-01-26) has tools reference =ui://= HTML resources that the host renders in a mandatory sandboxed iframe, talking JSON-RPC over postMessage; MIME type =text/html;profile=mcp-app=. Read via search summaries. [[https://modelcontextprotocol.io/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp][SEP-1865]]
- [I] The site would hold one or more frames per section. Edits regenerate a whole frame document, and the frame cannot share styles or state with the page except through messages.

** Rendering a page spec

Added 2026-10-28, after the brief decided that the assistant edits a per-visitor, ephemeral JSON page spec over a fixed component catalogue. The question here is what each renderer costs to draw that spec. Sizes are gzipped JS measured this pass: a minimal entry point built with esbuild =--minify=, then =gzip -9=, so they are close to the floor for each library (the method is under * Method).

- [O] Sizes measured on 2026-10-28 from npm: React 19.3.1 + react-dom 68,873 B; Preact 11.1.0 + @preact/signals 2.11.4 8,158 B; Lit 3.3.3 (=LitElement= + =html=) 5,842 B; htmx 4.0.0 =htmx.min.js= 13,026 B plus =ext/hx-sse.min.js= 2,519 B (htmx 2.0.11: 16,838 B); Chart.js 70,644 B; uPlot 23,006 B. Datastar's 11.90 KiB is the project's own figure. [[https://data-star.dev/][data-star.dev]]
- [I] *A chart library outweighs every renderer except React.* Preact, Lit, htmx and Datastar all ship under 16 KiB, while one chart library adds 22–69 KiB. The real gap between client renderers is React's extra ~60 KiB, which is acceptable for a site but not free.
- [I] *Ready-made spec renderers exist only for React and Lit.* json-render's React renderer and A2UI's React and Lit renderers (see above) cover the catalogue, streaming and binding for those two. Preact either goes through =preact/compat= (untested) or needs a hand-written renderer of about a hundred lines: a recursive switch from =type= to a component over the flat id map. The HTMX/Datastar route needs that same switch written as server templates.
- [I] *Incremental re-render is cheap everywhere once nodes have ids.* React needs care: =React.memo= per node, or a store with per-id selectors, so that a props patch does not re-render the tree. Preact signals and Lit give per-node updates by construction ([[https://preactjs.com/blog/introducing-signals/][Preact signals]], [[https://lit.dev/][lit.dev]]). On the server stacks, the server renders one component and the client morphs it by id ([[https://data-star.dev/reference/sse_events][Datastar SSE]], [[https://four.htmx.org/htmx-4][htmx 4]]).
- [I] *Charts are the awkward part of the server-rendered route.* A morph or swap would wipe a canvas the chart library drew. The chart must be a client custom element excluded from morphing (=data-ignore-morph= / =hx-morph-skip=, both [O] on the pages above), with its data passed as an attribute or signal. That puts a second, client-side half of the catalogue next to the server templates.
- [I] *Lit with dynamic tag names:* turn spec =type= into a tag through a fixed map (=document.createElement= or =unsafeStatic= on map values only). The model's =type= string must never reach =unsafeStatic=, which lit.dev says must be developer-controlled ([[https://lit.dev/docs/templates/expressions/][Lit expressions]]).
- [I] *The server-rendered route fits the ephemeral decision but makes the server stateful.* Each visitor's page spec would sit in server memory for the life of their SSE connection and be dropped on reload. That matches "gone on reload, no page store", but it conflicts with E3's thin, stateless key-holding server. The client renderers keep the spec in the browser, where the decision already puts it.

* Patterns

- [I] *Two families of what the agent emits.* Markup or code (HTMX, Datastar, vanilla, Alpine, generated JSX/Svelte, iframe) versus a JSON spec against a catalog (React/Preact/Lit/Svelte + registry, json-render, A2UI). Every stack can be driven either way; the choice between the families, not the framework, sets the safety and editing story.
- [I] *Stable ids are the shared edit primitive.* hx-swap-oob (by id), Datastar patch-elements (morph by id), json-render's =elements= map and A2UI's flat list all address sections by id. Incremental edits work wherever the agent can name a section.
- [I] *A server-held page goes with the hypermedia stacks.* HTMX and Datastar assume the agent loop and page state live on the server, so persistence and API secrets come free. Client stacks (React, Preact, Lit, Svelte, vanilla) keep state in the browser and need a store for anything beyond one session.
- [I] *A catalog is the safety line.* Safe designs have the renderer, not the model, own the markup: a component registry (React/Lit/Svelte/Preact), a server template set (HTMX/Datastar done safely), or an allowlist of custom elements (vanilla). Designs without a catalog fall back to sanitising (=setHTML=, DOMPurify) or iframes.
- [I] *Rich generated interactivity comes from prebuilt pieces or a sandbox.* Charts reach the page either as a prebuilt component or custom element (registry stacks, Web Components, Lit) or as code in an iframe. The HTML-fragment stacks need a JS island for charts.

* Bearing on the design (opinion)

This section is my evaluation, not observation.

- [I] *Open question "raw DOM/HTML or structured description":* I lean towards a structured description: a flat, id-keyed JSON page spec rendered from a small catalog. It answers R1 (patch one section by id), R2 (a =Chart= catalog entry takes fetched data, and "make it a bar chart" is a props patch), safety (no model-written markup) and persistence (store the JSON) at once. Model-written HTML is worth keeping only as a sandboxed-iframe escape hatch for one-off displays the catalog cannot express.
- [I] *R4, simplest stack:* React is not required for this. The spec plus catalog is the real design; the renderer can be React (most ready-made: json-render, A2UI), Preact+signals or Lit (smaller, buildless) at similar effort. React is the lowest-risk default because json-render and A2UI both support it.
- [I] *HTMX/Datastar are a real alternative if the agent loop runs on the server* (open question 3). The server holds the spec, renders fragments with its own templates, and streams them over SSE (Datastar natively, htmx 4 through its bundled =hx-sse= extension). The client then has almost no code. The cost is that charts need a JS island, and the server must render the catalog. This is the "major departure" that best fits "simpler is better"; Datastar suits streamed agent edits better than HTMX 2. /Added 2026-10-28:/ under the decided per-visitor, ephemeral page spec, this route also needs a stateful server that holds every visitor's spec in memory, against E3's stateless hybrid. That tilts R4 towards a client renderer: Preact+signals or Lit if bundle size matters, React for the ready-made renderers. See "Rendering a page spec".
- [I] *Avoid as the main mechanism:* in-page runtime JSX/Svelte compilation (unsafe without an iframe, brittle to edit) and raw =innerHTML= from the model.
