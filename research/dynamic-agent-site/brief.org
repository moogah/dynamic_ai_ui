Started 2026-10-28. Evidence in =evidence/=, threads in =threads/=, probes in =probes/=. No code root yet; terms live in this brief.

* Why

User, 2026-10-28:

#+begin_quote
I want to explore the concept of a 'dynamic agent driven website'. This will be a site that comes with a bare skeleton of structure and the ability to chat with an AI assistant. The assistant will have tools that let it change the structure and content of the site.

Some elements we'll need: the core LLM loop (REPL, state machine, tool calls)
Tools for interacting with the DOM

I think React can very likely handle the dynamic needs, but I also want to explore other options, including some major departures from the norm like HTMX. Simpler is better, if it can do what we need.

The assistant will also need to have tools for making API calls to gather data, and it will read that data and decide how to display it based on conversations with the user.
#+end_quote

* Purpose

An experiment (user, 2026-10-28): to learn how well an agent can reshape a page and which stack suits it. Done when the user has seen it work and knows what is hard about it; rough edges are acceptable. Judged by open-ended play, not a scripted test set.

* Goals

- *R1. The site starts as a skeleton and the assistant reshapes it.* A visitor asks in chat for a section, layout or content change and sees it appear on their page without a reload or a developer; the change lasts for that visit only.
- *R2. The assistant fetches data and chooses how to show it.* Asked for e.g. "the weather for my city as a chart", it calls an API on the owner's allowlist, reads the result and renders a display the visitor can then refine in conversation. Adding a source means adding a host (and secret) to the list, not writing code.
- *R3. A hand-written core agent loop.* Chat in, model call, tool calls executed, results fed back, until the model stops; with explicit states (idle, calling the model, running tools, awaiting the visitor, error) the UI can show. Written by hand so the mechanics are visible; no agent framework.
- *R4. Simplest stack that does the job, renderer swappable.* One build: React (or Preact) draws the page spec through a fixed component catalog. The page spec and the tools do not depend on the renderer, so a second renderer could be added without changing them.
- *R5. Visitors need nothing but a browser.* The site owner's small server supplies the Claude key and the data-API secrets; it stores no page or conversation.
- *R6. A data-capable component catalog.* About ten components (heading, text, image, card, list, row/column container, table, chart, key-figure tile, form/button) so requests like "chart this" or "show as a table" work.
- *R7. Undo the assistant's last turn.* A button restores the page spec as it was before the assistant's last turn, so mistakes are cheap during play.

* Non-goals

- A full version history or timeline of page states (2026-10-28: single-step undo only).
- An agent framework (Vercel AI SDK, LangGraph, OpenAI Agents SDK) for the loop (2026-10-28).
- Building on two stacks to compare them in this experiment (2026-10-28).
- A fixed acceptance suite of scripted conversations (2026-10-28: judged by open-ended play).
- Product concerns: multi-tenant use, cost controls and abuse protection for public visitors, polish, docs for other site owners (2026-10-28: the purpose is an experiment).
- Fetching from arbitrary URLs outside the owner's allowlist (2026-10-28).
- Letting the assistant write raw HTML or scripts into the page (2026-10-28: it edits the page spec only).
- Persisting a visitor's page across reloads, accounts, or a shared site edited for other visitors (2026-10-28: changes are for this visitor only and vanish on reload).

* Terms

Moved to [[file:../../docs/glossary.org]] at the hand-off, 2026-10-28.

- *page spec* (agreed 2026-10-28): the structured JSON description of the current page, a list of components with ids plus the data they show; the assistant edits it and the page is drawn from it. Example: "the assistant added a chart to the page spec." Avoid: DOM, layout, schema.

- *component catalog* (agreed 2026-10-28): the fixed list of component types the page knows how to draw (e.g. chart, table, card); the page spec may only use types from it. Example: "add a map component to the catalog so the assistant can show locations." Avoid: widget library, design system; spell it "catalog", not "catalogue".

* Assumptions

- React can handle the dynamic needs. Origin: the user, stated as likely; E1 found every client renderer adequate and small next to the chart library, so it holds.
- "Tools for interacting with the DOM" means tools that change the page. Origin: the user's words; settled 2026-10-28 as tools that edit the page spec, which the renderer draws, not direct DOM edits.
- The visitor-facing site is used by the owner and a few people they invite, so cost and abuse controls can wait. Origin: inferred from the purpose (an experiment); not stated by the user.
- Fetched API responses can be trimmed to fit the model's context without losing what the visitor asked about. Origin: E3; untested, a likely "what's hard".

* What the evidence shows so far

Descriptive; each line cites its evidence file.

- *What the agent emits matters more than the framework.* A flat JSON page spec over a fixed set of allowed components can be edited one section at a time, is XSS-safe (the model writes no markup) and persists as plain JSON; Vercel json-render and Google A2UI standardise such specs with renderers for React, Lit, Svelte and others (E1).
- *Two independent declarative specs converged on one shape.* Google A2UI and Vercel json-render (both Apache-2.0): a flat list of components keyed by id, a separate data model bound by path, a client-owned component catalog, edits as upserts or JSON patches. A2UI's four messages (create surface, update components, update data, delete surface) could serve as the tool schema (E2).
- *Own minimal page spec in json-render's shape, A2UI-style tools.* A2UI's messages nearly fit as tools, but re-sending an id replaces props rather than merging, it has no remove-component message, v1.0 renames binding keys and its React renderer does not yet support 1.0. E2 (opinion) recommends defining our own small spec shaped like json-render, edited by upsert-by-id, remove and set-data tools. Thesys C1 is archived in favour of OpenUI (E2, revised).
- *Most other prior art either embeds widgets in chat or regenerates whole HTML.* AI SDK, MCP Apps and OpenAI Apps SDK put prebuilt widgets in chat messages; Artifacts, websim and tldraw make-real regenerate full HTML in a sandboxed iframe; only the latter reshape a whole page. Several of those rows rest on search snippets (E2).
- *HTMX-style is viable only with a stateful server-side loop.* htmx 4 (via its bundled =hx-sse= extension) or Datastar can render fragments from the page spec on the server and stream them over SSE, but the server must then hold each visitor's page spec in memory, which conflicts with the stateless key-holding server decided on; Datastar's documented risk is =data-*= expressions running as JavaScript (E1, revised from primary sources).
- *Client renderers are all small next to the chart library.* Preact+signals about 8 KiB gz, Lit about 5.7 KiB, React about 67 KiB (with ready-made A2UI/json-render renderers), against 22-69 KiB for a chart library (E1).
- *API keys decide where the model is called from.* Confirmed from primary sources: without the opt-in browser header the API response carries no CORS headers, and with it the key is exposed; as of 2026-10 Anthropic has no browser-safe per-visitor token (App Attest is iOS/macOS only; Workload Identity Federation is for server workloads). A server proxy is required (E3, revised).
- *Server loop with browser-run tools costs no extra round trip.* Both it and a browser loop behind a thin proxy send tool results in a new model request. Vercel AI SDK client-side tools (no =execute=, =onToolCall=, =addToolOutput=, v7) fit the page spec and per-visitor decisions with a stateless server that pins the system prompt and tools; E3 now weighs a hand-written loop plus proxy and AI SDK =useChat= as equal (E3, revised).
- *The loop itself is small.* About 30 lines: call model, run tool calls, feed results back, stop on end of turn; states idle / calling / running tools / awaiting user (E3).
- *API-call tools are safer as registered connectors than a generic fetch.* Calls made from the server hold secrets and a host allowlist, avoiding CORS and SSRF (the IETF draft adds checking the resolved IP and not following redirects); E3's opinion was to defer a generic =http_fetch=; the user chose an allowlisted generic fetch instead (Decided 2026-10-28).
